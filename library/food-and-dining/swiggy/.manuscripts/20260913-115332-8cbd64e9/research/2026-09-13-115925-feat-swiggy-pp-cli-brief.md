# Swiggy CLI Brief

## API Identity
- Domain: Swiggy Builders Club — Swiggy's official MCP (Model Context Protocol) commerce platform. Three independent servers: **Food** (restaurant discovery/ordering/tracking, 20 tools), **Instamart** (quick-commerce grocery, 19 tools), **Dineout** (table reservations, 12 tools). 51 tools total, confirmed by direct enumeration of every reference page.
- Users: Agent/CLI developers building India-first commerce agents on top of Swiggy. Launched 2026-04 (v1.0), invite-based for production; local dev and OAuth against the real production auth server are free and unrestricted.
- Data profile: Highly stateful, multi-step commerce flows (search → cart → coupon → pay → track) rather than flat CRUD resources. Every domain object (address, cart, order, booking) is an opaque server-assigned string ID threaded through a specific sequence of calls — there is no direct "list everything" browsing outside restaurant/product/table search.

## Architectural Reality Check (read before generating)
This is **not a REST/OpenAPI API** — it is a genuine MCP server: JSON-RPC 2.0 over HTTP, one POST endpoint per domain (`mcp.swiggy.com/food`, `/im`, `/dineout`), method `tools/call` with `{name, arguments}` params, wrapped in MCP's Streamable HTTP transport (an `initialize` handshake precedes `tools/call` traffic). Confirmed by researching `cli-printing-press`'s own generator (see [references/spec-format.md](../../../../../.claude/skills/printing-press/references/spec-format.md) and phase files): **there is zero native MCP/JSON-RPC awareness or OAuth 2.1 PKCE+DCR support in the generator.** `generate --spec` assumes one HTTP-verb+path = one REST operation with standard security schemes. Hand-authoring an OpenAPI doc that fakes 51 tools as 51 POST operations on one path is a bad fit — it won't produce the `tools/call` envelope, session-reuse semantics, or PKCE+DCR login.

**Chosen approach:** Use the internal YAML spec format's `resources`/`endpoints` shape as scaffolding to enumerate all 51 tools (one endpoint per tool, grouped by resource = server), each POSTing a JSON-RPC-shaped body to that server's single path — then hand-write (a) the shared JSON-RPC/MCP transport client (session-id reuse, no-reinitialize-per-call) and (b) the OAuth 2.1 PKCE + Dynamic Client Registration login command as novel code, following [references/oauth2-pkce-cli-checklist.md](../../../../../.claude/skills/printing-press/references/oauth2-pkce-cli-checklist.md). Treat this as "generate scaffolding, then heavily hand-extend," not pure spec-driven generation. Budget real engineering time in Phase 2/3 for the custom transport + auth layers — this is the single biggest risk to the 30-60 minute norm for this run.

## Reachability Risk
- **Low for auth/transport reachability, but docs are internally inconsistent — verify empirically, don't trust prose alone.**
- Verified live by direct probe (2026-09-13): `GET /.well-known/oauth-authorization-server` returns full RFC 8414 metadata including `registration_endpoint`. `POST /auth/register` (Dynamic Client Registration, RFC 7591) is **live and functional** — returned `201` with a real `client_id` for a `redirect_uris: ["http://localhost:8765/callback"]` registration. This contradicts the platform changelog, which lists "OAuth 2.1 Dynamic Client Registration (RFC 7591)" under the **v1.1 roadmap ("not yet shipped")** — the changelog is stale; trust the empirical probe.
- Countervailing finding: `GET /.well-known/oauth-protected-resource` (RFC 9728) does **not** actually exist — it 404s to the Swiggy consumer-site fallback HTML, despite `authenticate.md` documenting it as a real endpoint. Don't rely on it; use the authorization-server metadata document instead.
- Unauthenticated `POST /food` with an `initialize` JSON-RPC body correctly returns `401` with a standard `WWW-Authenticate: Bearer` challenge — confirms the endpoint is live and auth-gated as documented. Full `initialize` → `tools/call` session behavior (whether the server issues an `Mcp-Session-Id` that can be reused across separate CLI process invocations, or requires a live persistent connection) is **not yet verified with a real token** — this is the one open question that must be resolved empirically during Phase 5 (dogfood/live testing) once a real user completes the phone+OTP OAuth flow. Design the transport layer to support both (reuse a stored session id if present; fall back to re-initializing) and confirm which one the server actually requires.
- Production access is invite-gated (`Swiggy Builders Club support` review), but **local development is not** — OAuth against the real production auth server, with a `localhost` redirect URI, works today without any application/approval (confirmed via the DCR probe above). The generated CLI can be built and dogfooded end-to-end without applying for anything.
- Probe-safe endpoints used: `GET https://mcp.swiggy.com/.well-known/oauth-authorization-server` (200, no auth), `POST https://mcp.swiggy.com/auth/register` (200/201, no auth, DCR is designed to be public), `POST https://mcp.swiggy.com/food` with an unauthenticated `initialize` call (401, expected).

## Top Workflows
1. **Order food end-to-end** (7-tool canonical flow): `get_addresses → search_restaurants → get_restaurant_menu → update_food_cart → [fetch_food_coupons → apply_food_coupon] → get_food_cart → place_food_order → track_food_order`. Hard ₹1000 cart cap on Builders Club orders; `place_food_order` is explicitly **not idempotent** — on 5xx, the client must call `get_food_orders` to check whether the order actually placed before ever retrying.
2. **Order groceries (Instamart)**: `get_addresses → search_products → update_cart → [list_coupons → apply_coupon] → get_cart → checkout → confirm_order → track_order`. Mirrors the Food flow but Instamart's mutating verb is `checkout` (not `place_*_order`), and cart/coupon calls use a `cartKey`.
3. **Book a table (Dineout)**: `get_saved_locations → search_restaurants_dineout → get_restaurant_details → get_available_slots → create_cart → book_table → get_booking_status`. Requires `lat`/`lng` explicitly (not auto-resolved from address like Food/Instamart).
4. **Pay with UPI** (shared stage across all 3 servers): `get_payment_options → place-order-tool(paymentMethod:"UPI", intentApp|generateUPIQR) → check_payment_status (long-poll, ~19s server hold, poll until terminal) → confirm_order → track/status`. `confirm_order` args differ per server: Food uses `orderId+addressId+lat+lng` (no `paasId`); Instamart/Dineout use `orderId+paasId`. COD is the universal fallback when UPI isn't offered.
5. **Reorder / go-to items (power-user shortcut)**: Instamart's `your_go_to_items` replaces 3-5 search calls for a returning user — explicitly recommended by Swiggy's own docs for low-latency voice/repeat-order surfaces. A `swiggy instamart quick-reorder` command built on this tool is a strong differentiator.

## Table Stakes
- Every server needs: search/browse, cart management (get/update/clear/flush), coupon apply, payment-option discovery, order placement, order confirmation, order tracking, and `report_error` (identical 6-param shape across all three servers — a shared diagnostic tool, not domain-specific).
- Address book CRUD (`get/create/delete_address`) is close to byte-identical between Food and Instamart (14 shared params) — worth a shared internal type/command in the CLI rather than three separate implementations.
- Standard `{success, data, message}` / `{success:false, error:{message, reportLink?, reportHint?}}` envelope on every tool, across all three servers — one shared response-parsing layer covers all 51 endpoints.
- No symbolic `error.code` yet (roadmap item) — must classify failures by `error.message` prefix + HTTP status per the documented bucket table (auth/bad-input/upstream-timeout/upstream-error/domain-failure/internal-error) and code that classifier once, shared across all commands.

## Data Layer
- Primary entities worth a local SQLite store: **saved addresses** (Food/Instamart, low-churn, cache aggressively per Swiggy's own rate-limit guidance), **order/booking history** (all 3 servers — `get_food_orders` / `get_orders` / booking status lookups), **applied-coupon history**, and **cart snapshots** (useful for a `swiggy cart show` command that doesn't need a live round-trip after the first fetch in a session).
- Sync cursor: order/booking lists paginate via `offset` + response-side `nextOffset`/`hasMore` — standard offset pagination, consistent across every search/list endpoint in the catalog.
- FTS/search: local full-text cache over restaurant/product search results makes sense for a `swiggy food search --offline` fallback and for building the CLI's own history/favorites view without re-hitting rate limits — directly serves Swiggy's own "cache low-churn data, don't re-fetch every turn" guidance.
- OAuth token + MCP session state (access token, expiry, per-domain session id if the server issues one) belongs in the CLI's secure config store, never the SQLite data store — treat it like any other credential material.

## Codebase Intelligence
- Source: direct API documentation research (mcp.swiggy.com/builders/docs), not DeepWiki (no public GitHub repo backs this API — it's a first-party hosted service).
- Auth: OAuth 2.1 Authorization Code + PKCE (S256), Dynamic Client Registration (RFC 7591, confirmed live), `Authorization: Bearer <token>` header. Access tokens live 5 days; **no refresh-token issuance in v1.0** (roadmap for v1.1) — re-run full OAuth on expiry, always treat 401 as "re-authenticate," never cache success assumptions.
- Data model: no shared entities across servers — Food, Instamart, and Dineout do not share carts, orders, sessions, or addresses (Instamart/Food addresses are similar in shape but are separate records per server, each with its own `create/get/delete_address` triplet).
- Rate limiting: 70 req/min per authenticated user per server (30/min for write/mutating tools), burst = 2x steady-state for 10s windows, keyed on the authenticated user. `X-RateLimit-*` headers are documented but **not yet enforced in v1.0** (traffic is shed upstream instead) — code defensively for both today's shedding behavior and tomorrow's header-driven throttling.
- Architecture: the single most-repeated operational instruction across every Swiggy doc page is **do not reconnect/reinitialize per tool call** — one persistent session per domain, sequential (not parallel) domain initialization, and the #1 documented cause of real integrators tripping rate limits is exactly this mistake. This must be a first-class constraint on the generated CLI's transport layer, not an afterthought.

## User Vision
- User asked for a CLI for Swiggy, pointed at the Builders Club API reference docs, and asked for thorough study of the page plus how to authenticate — no additional feature requests beyond "build the best CLI for this API."

## Product Thesis
- Name: **swiggy** (binary: `swiggy-pp-cli`)
- Why it should exist: Swiggy's Builders Club is brand new (launched 2026-04) and MCP-native — every existing integration path assumes an LLM agent driving tool calls through a generic MCP client (`mcp-cli`, `mcp-use-cli`) with zero domain knowledge, or a bespoke agent framework integration. No purpose-built human-facing CLI exists today: a developer who wants to `curl`-test a flow, inspect their saved addresses, or dry-run a cart before wiring up a full agent has to hand-write JSON-RPC envelopes by reading 51 separate reference pages. This CLI turns that into `swiggy food search-restaurants --query biryani`, with a local address/order/coupon cache, one shared error classifier across all 51 tools, a single persistent OAuth session (respecting Swiggy's own don't-reinitialize guidance instead of violating it like a naive per-call implementation would), and safety rails baked in for Swiggy's own documented gotchas (₹1000 cart cap, non-idempotent order placement, UPI long-poll payment confirmation).

## Build Priorities
1. **Transport + auth core first**: OAuth 2.1 PKCE + DCR login command (loopback callback, per the checklist), persistent JSON-RPC/MCP session client with token storage and 401-triggers-reauth handling, and the shared error-envelope classifier. Nothing else works without this.
2. **Food + Instamart command surfaces** (39 of 51 tools): address book, search, cart, coupon, checkout/place-order, payment (COD + UPI long-poll), tracking — these are the highest-volume, highest-demo-value flows.
3. **Dineout command surface** (12 tools) plus the cross-cutting `report_error` and local SQLite cache (addresses, order/booking history, search cache) for offline browsing and the "don't re-fetch low-churn data" behavior Swiggy's own docs ask integrators to build.
